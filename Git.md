# Правила работы с Git в этом проекте

Инструкция для Claude. Файл переносится в любой проект как есть.

## Главный принцип

Git здесь — **облачный бэкап на уровне версий**, а не журнал правок.
Мелкие шаги внутри работы не отслеживаются: их контекст Claude и так держит
в памяти проекта. В Git должны попадать только **крупные, осмысленные
изменения**, между которыми имеет смысл смотреть diff.

## Что НЕ делать

- Не дробить работу на мелкие коммиты (`feat: то`, `fix: сё`, `style: пробелы`)
- Не спрашивать «закоммитить?» после каждой правки
- **Не создавать релизы по своей инициативе** — только по явной команде
- Не коммитить и не пушить без явной просьбы
- Не использовать `reset --hard` и `push --force` на том, что уже в облаке

## Цикл релиза

Запускается **только по команде пользователя**. Накопленные изменения
оформляются целиком:

```bash
# 1. Один коммит на весь блок работы
git add -A
git commit -m "краткая суть

Что изменилось для пользователя — по пунктам."

# 2. Аннотированный тег (обязательно -a, не голый git tag)
git tag -a vX.Y.Z -m "vX.Y.Z — название версии

Новое:
- ...

Исправлено:
- ..."

# 3. Пуш: ветка и тег ОТДЕЛЬНО, теги сами не уезжают
git push origin main
git push origin vX.Y.Z

# 4. Release с человеческим описанием
gh release create vX.Y.Z --title "vX.Y.Z — название" --notes-file notes.md

# 5. Описание репозитория на GitHub - под то, чем проект стал
gh repo edit <user>/<repo> --description "..."
```

**Пятый шаг не пропускать.** Описание репозитория — первое, что видят
в поиске и в списке проектов, а устаревает оно незаметно: код уехал вперёд,
а в шапке всё ещё старое обещание. Раз в релиз перечитать его и поправить,
если разошлось с делом. Заодно проверить `homepage` и темы.

## Нумерация версий

`MAJOR.MINOR.PATCH` — но следовать той схеме, которая уже есть в репозитории,
а не навязывать строгий семвер. Если номер неочевиден — спросить.

| Что произошло | Бамп |
|---|---|
| Починил баг, ничего не сломав | PATCH: `1.0.0` → `1.0.1` |
| Добавил фичу, старое работает | MINOR: `1.0.1` → `1.1.0` |
| Сломал совместимость | MAJOR: `1.1.0` → `2.0.0` |

## Описание релиза

Строится вокруг **что изменилось для пользователя**, а не вокруг списка
коммитов. Список коммитов — максимум справочным блоком в конце.

Структура: `✨ Новое` → `🐛 Исправлено` → `⚠️ Ломающие изменения` →
`🔄 Совместимость` → ссылка на полный diff вида
`https://github.com/<user>/<repo>/compare/vA...vB`

Черновик описания писать во временную папку, а не в репозиторий.

## Откаты

Если что-то сломалось — откатываемся к нужной версии.

```bash
git diff vA vB              # что изменилось между версиями
git log --oneline vA..vB    # какие коммиты вошли

git revert <sha>            # откат обычного коммита
git revert -m 1 <merge-sha> # откат merge-коммита
```

Правила:

- **Всегда `revert`**, если коммит уже запушен. `reset --hard` — только для
  локального, ещё не отправленного в облако
- Откат — это изменение текущего состояния ветки. **Теги и Releases остаются
  на месте**: «в проде откатились, но релиз в истории остался»
- После отката показать доказательство: `git diff <целевой-тег> HEAD` пуст
- Ловушка: после `revert -m 1` повторный `git merge` той же ветки скажет
  «уже актуально». Вернуть изменения — только через `revert` самого отката
- Если всё сломалось — `git reflog` помнит все состояния HEAD за недели

## Перед пушем

Пользователь работает и в терминале, и в веб-интерфейсе GitHub — истории
могут разойтись. Перед пушем:

```bash
git fetch origin
git log main..origin/main   # что появилось в облаке без меня
```

`! [rejected]` — не поломка, а сигнал что на сервере есть чужие коммиты.

## Окружение

- `gh.exe` может отсутствовать в PATH запущенной сессии — полный путь:
  `C:\Program Files\GitHub CLI\gh.exe`
- `gh auth login` интерактивен, через инструменты не запускается —
  просить пользователя выполнить вручную

## Общение

Объяснять смысл команд, а не просто выполнять. После структурных изменений
показывать граф:

```bash
git log --oneline --graph --decorate --all
```
